## Уточнения автора после обсуждения — имеют приоритет над первоначальным предложением ниже

- Сначала локальная PocketBase и четыре примера, затем проверка и перенос на VPS. Looping позже.
- Название и заполненная/контурная части заголовка переводятся отдельно на FR/EN/RU. Для каждого языка форма содержит два обычных текстовых поля; никакого HTML/JSON вручную. Полное название получается соединением частей с явно заданным пробелом или без него. Переводы названия и описания обязательны при публикации; основной язык FR.
- Галерея содержит 1–4 медиа суммарно: изображения, либо одно видео и изображения, либо только одно видео. Если видео есть, оно всегда первое. Отдельная обязательная обложка-изображение отменяется: главным медиа для страницы, карточки и главной служит первое медиа галереи. Постер видео опционален и нужен как резерв, не как обязательная замена видео.
- Порядок хранится в position у записей project_media. Отдельные поля «картинка 1/2/3/4» не нужны. Интерфейс переставляет изображения кнопками; видео закрепляет на первом месте. Проверяем уникальные позиции внутри проекта.
- Видео: autoplay, muted, loop, playsinline. Пауза при уходе из видимости или выборе другого слайда. Автозапуск зависит от браузера; при блокировке нужен доступный ручной запуск. Звука по умолчанию нет. На главной видео тоже может быть главным медиа под бумажной маской.
- Очень вытянутые работы показываем целиком без обрезки, с возможностью увеличения, а не уменьшаем до нечитабельной полосы.
- Характеристики опциональны, число отображаемых карточек не ограничиваем тремя/четырьмя. Две колонки на широком экране, нечётная последняя слева; высота по содержимому.
- Дополнительное содержимое этапа пока обсуждается: изображение + маленькая заметка + опциональная кнопка. Не делаем широкую картинку с мелким текстом единственным решением для телефона. Для текстовых схем предпочтительны адаптивные блоки; для уникальной иллюстрации возможен отдельный мобильный вариант. Окончательно выберем до создания полей этапов.
- Stonehenge: personal, Blender, 2024. Афиши Montbéliard: university, Illustrator по последнему выбору автора; часть работы завершалась в Affinity. Не объявляем их профессиональным заказом.
- Локальный исполняемый файл PocketBase 0.40.4 подготовлен в соседней папке Documents/ChatGPT/Base-de-donnees-Portfolio, вне репозитория. Коллекции ещё не создавались.

## 1. Одна универсальная страница

Порядок: заголовок → категория, тип работы и год → галерея слева / описание и характеристики справа → этапы на всю ширину → предыдущий проект, все проекты, следующий проект. На телефоне всё становится одной колонкой: галерея, описание, характеристики, этапы. Пустые опциональные поля не создают карточек или пустых отступов.

Заголовок делится на две части: заполненная и контурная. Это редакционные поля, а не автоматическое разрезание слова пополам: «Éclo» + «voix», «Stone» + «henge», либо первая строка + вторая строка. Обе части остаются одним смысловым h1. Название работы по умолчанию не переводится, но можно дать перевод по желанию.

Галерея сохраняет пропорции оригинала, без обрезки афиши или картины. Основная картинка — object-fit: contain. У вертикальной обложки миниатюры слева, у горизонтальной — снизу; на телефоне всегда снизу. Решение определяется пропорциями обложки, с простым ручным переключателем «авто / портрет / пейзаж». Одна картинка — без стрелок, точек и миниатюр. При нескольких картинках — доступные кнопки, управление клавиатурой, подписи и alt. Видео запускается по нажатию, без автоматического звука; его постер — обычное изображение.

Этапы всегда идут сверху вниз. Номер генерируется из позиции: 01, 02… Нет ограничения в три этапа. Заголовок и описание имеют единый стиль; дополнительные блоки находятся под описанием. Палитру и ссылку Éclovoix переносим под текст соответствующего этапа. Это делает редактирование и мобильную версию предсказуемыми. Высота карточек зависит от текста.

| Данные | Все проекты | Особенности |
|---|---|---|
| Название, постоянный slug | обязательно | slug одинаковый для FR/EN/RU |
| Категория | одна, обязательно | web, graphic-print, 3d, drawing-painting, motion-video |
| Тип работы | обязательно | personal / university / professional |
| Год выполнения | обязательно | не дата добавления на сайт |
| Описание | обязательно на FR при публикации | EN/RU переводятся отдельно |

| Контекст | опционально | отдельный текст, не повторяет автоматически тип работы |
| Роль | опционально | обычно web, графика, 3D, монтаж |
| Инструменты | опциональный список | только программы, реально использованные в данной работе |
| Техника | опциональный текст | например «гуашь на холсте» |
| Формат | опциональный текст | «30 × 30 см», «A3»; можно использовать и у афиш |
| Этапы | 0…N | рисунок может не иметь этапов вообще |
| Ссылки | 0…N | сайт, Behance, опубликованное видео; не только сайты |
| Акцент | автоматически предложенный + ручная поправка | сохраняется в базе, не вычисляется при каждом посещении |

Категория описывает дисциплину, тип — обстоятельства создания. Монтаж для художницы может быть professional, даже если работ всего две. Смешанному проекту выбираем основную категорию; дополнительные категории пока не вводим, чтобы фильтры оставались понятными. Если реально понадобятся несколько дисциплин у одной работы, заменим одинарную связь на множественную. Инструменты и этапы не зависят жёстко от категории: поля разрешены всем, но форма показывает подходящие подсказки.

В макетах есть несогласованные исходные данные: у афиш бейдж «Modélisation 3D» и personal, хотя описание говорит об университетском брифе; Illustrator в карточке, Affinity в производстве. У Stonehenge указан 2024 в карточке, а 2025 в описании. Перед наполнением надо уточнить реальные значения; не переносим эти расхождения автоматически.

## 3. Концептуальная схема для Looping (MCD)

КАТЕГОРИЯ (0,N) — классифицирует — ПРОЕКТ (1,1).
ПРОЕКТ (0,N в черновике; 1,N при публикации) — содержит — МЕДИА (1,1).
ПРОЕКТ (0,N) — содержит — ЭТАП (1,1).
ПРОЕКТ (0,1 в черновике; 1,1 при публикации) — выбирает обложку — МЕДИА (0,1).

Обложка должна принадлежать этому же проекту и быть изображением. Отдельная таблица связи «проект–категория» не нужна при одной категории: relation хранится в projects. Если станет несколько категорий, тогда в реляционной MLD появится таблица связи. В PocketBase сущности называются коллекциями, записи — records, соединения — relation.

Аккаунт редактора — техническая сущность аутентификации, не автор каждой работы. Мы не добавляем ненужную связь «пользователь владеет проектом», потому что портфолио одного автора.

Схема рядом: projects-schema.mmd. Она переносится в Looping вручную через сущности и связи; это не файл .loo. JSON-поля ниже — практическое решение для небольших вложенных блоков. Они не являются строго нормализованными таблицами MCD. Если преподаватель требует полноценную нормализацию переводов/блоков, до создания базы выделим сущности ПЕРЕВОД и БЛОК, сохранив эту же структуру интерфейса.

## 4. Предлагаемые коллекции PocketBase

### categories

| Поле | Тип | Правило |
|---|---|---|
| slug | text | обязательный, уникальный, постоянный |
| label | JSON переводов | {fr, en, ru}, FR обязателен |
| sort_order | number | положительное целое, порядок групп в каталоге |

Отдельных страниц категорий нет. Начальные записи: Web & interfaces, Design graphique & print, Modélisation 3D, Peinture & dessin, Motion & vidéo.

### projects

| Поле | Тип | Правило |
|---|---|---|
| slug | text | обязательный, уникальный, латинские буквы/цифры/дефисы |
| title | text | обязательное название, не меняется при переключении языка |
| heading | JSON | {filled, outline}; outline может быть пустым |
| category | relation → categories | одна обязательная категория |
| work_type | select | personal, university, professional |
| completed_year | number | обязательное целое, показываем и сортируем именно его |
| content | JSON переводов | FR/EN/RU: description, context, role, technique, format |
| tools | JSON array | названия инструментов, например ["Blender"] |
| cover | relation → project_media | одно изображение, обязательно при публикации |
| gallery_layout | select | auto, portrait, landscape |
| links | JSON array | {label:{fr,en,ru}, url}; только http/https |
| accent_auto | text | вычисленный HEX #RRGGBB |
| accent_override | text | необязательная ручная замена |
| priority_rank | number | 0 = обычная работа; 1, 2… = закреплённая позиция в каталоге |
| home_rank | number | 0 = не выводить как избранный проект на главной; 1, 2… = порядок |
| status | select | draft / published, по умолчанию draft |

id, created, updated — технические поля PocketBase; created/updated добавляются как autodate при настройке коллекции. content — обычный текст с абзацами, не HTML. В форме это отдельные поля, JSON пользователю не показывается.

В начале FR — основной язык. EN/RU могут быть незаполнены: тогда отображается FR с честной отметкой языка, а не выдуманный перевод. Перед полноценной публикацией трёх языков проверяем переводы описаний, подписей и этапов. Название и технические названия программ не требуют перевода.

### project_media

| Поле | Тип | Правило |
|---|---|---|
| project | relation → projects | одна обязательная работа |
| kind | select | image / video |
| purpose | select | gallery / detail (для изображения в этапе) |
| position | number | порядок внутри галереи |
| image | file | один файл для image; для video — постер, если выбран этот способ хранения |
| external_url | url | альтернативный адрес изображения либо видео |
| provider | select | pocketbase / external; имя конкретного сервиса позже |
| provider_asset_id | text | необязательный идентификатор, помогает обслуживать внешний файл |
| width, height | number | исходные размеры для сетки, обязательны у изображения при публикации |
| alt | JSON переводов | смысловое описание, FR обязательно у изображений |
| caption | JSON переводов | необязательная видимая подпись |

У изображения один источник: file ИЛИ external_url. У видео внешний адрес либо идентификатор разрешённого плеера, плюс необязательный постер. Адрес плеера и прямой MP4 — разные вещи: форму и компонент определяет выбранный провайдер. Не вставляем произвольный iframe/HTML. Детальные изображения не входят в лимит четырёх изображений галереи. Для них также есть alt.

### project_sections

| Поле | Тип | Правило |
|---|---|---|
| project | relation → projects | одна обязательная работа |
| position | number | положительное целое, уникально внутри проекта |
| title | JSON переводов | обязательное название на FR |
| description | JSON переводов | основной текст, может отсутствовать при содержательном блоке |
| blocks | JSON array | упорядоченный список готовых блоков; пустой список допустим |

Номер не храним: он получается из порядка. Отдельные записи этапов легче переставлять и редактировать, чем одно огромнейшее поле проекта. Изображения в blocks ссылаются на project_media по id. При удалении медиа проверяем ссылки и обложку; не оставляем битые ссылки. При удалении проекта удаляем дочерние медиа и этапы, а внешние файлы удаляем отдельно после проверки, что они нигде не используются.

### editors (auth)

Один аккаунт, создаваемый владельцем через системную панель PocketBase. Публичной регистрации нет. Страница /admin сайта — будущий удобный интерфейс работы с проектами; системная панель PocketBase остаётся для настройки базы. Пароли и токены суперпользователя в код сайта не попадают. Обычному аккаунту редактора достаточно прав редактирования контента.

## 5. Дополнительные блоки этапа — без кода в базе

| Тип | Поля формы | Как выглядит |
|---|---|---|
| note | текст | небольшая приглушённая строка |
| palette | список HEX и подписи, необязательный заголовок | круги одинакового размера, перенос на телефоне |
| process | список коротких шагов | текст со стрелками, адаптивный перенос |
| quotes | 1–3 коротких фразы | колонки; основной текст + необязательная выделенная часть |
| image | выбор detail-медиа | схема/иллюстрация, подпись и alt |
| link | подпись и URL | общая контурная кнопка |

Форма: «Добавить блок» → выбрать тип → заполнить его поля. Кнопки ↑/↓ меняют порядок; «Удалить» убирает блок. Можно соединить palette + process или note + link. Для сложной уникальной схемы используем image, но заголовок и описание остаются живым текстом. Цвет, размер шрифта и произвольные стили не предлагаются: единый дизайн задаётся компонентами. Палитра содержит реальные цвета проекта, а не меняет общий дизайн страницы.

Примеры соответствия макетам:

| Работа | Характеристики | Этапы и блоки |
|---|---|---|
| Carnaval des Profondeurs | техника, год, формат | без этапов |
| Éclovoix | технологии, роль, год | Problématique; Conception + palette + process; Solution + note; Réalisation + link |
| Stonehenge | контекст, роль, Blender, год | Concept; Objectif; Processus — без дополнительных блоков |
| Montbéliard | контекст, роль, инструмент, год | Brief + quotes; Approche + palette + process; Production + note |

## 6. Порядок и фильтры

Фильтры: категория, тип работы, год. Они ограничивают список и могут сочетаться. Сортировка: рекомендуемые; сначала новые; сначала старые; по категориям. «По категориям» собирает группы в порядке categories.sort_order, внутри каждой — рекомендуемые.

Рекомендуемые: проекты с priority_rank > 0 идут первыми по возрастанию; остальные — completed_year по убыванию, затем slug для стабильности. Например Éclovoix = 1, афиши = 2, Stonehenge = 3; остальным ничего назначать не нужно. Две закреплённые работы не могут иметь одинаковую положительную позицию: форма предлагает сдвинуть соседнюю запись. Значение 0 разрешено многим. Сортировка «сначала новые» игнорирует закрепление — иначе выбор посетителя не работал бы честно.

Главная независима: home_rank определяет только избранные работы. Возможность поставить сайт первым на главной не должна менять каталог. Блок личных рисунков на главной может быть подборкой категории drawing-painting, а не четвёртым одиночным проектом. Эту подборку настроим отдельно при наполнении главной.

Для начала достаточно кнопок «выше / ниже» и «закрепить», без перетаскивания. Числа хранит база, а пересчёт делает интерфейс. Предыдущий/следующий проект используют опубликованные работы в рекомендуемом порядке; на первом/последнем не показываем несуществующего соседа.

## 7. Медиа и надёжность

Моё предложение для нынешнего небольшого портфолио: изображения хранить в file-полях PocketBase на постоянном диске VPS, видео — во внешнем видеосервисе; если существующий сервис действительно поддерживает оба типа медиа и удобную загрузку, можно хранить там и изображения. Модель уже допускает external_url, поэтому менять весь сайт не придётся. До выяснения провайдера ничего не переносим и не заводим платную подписку.

PocketBase официально поддерживает локальный pb_data/storage и S3-совместимое хранилище. Отдельный медиахостинг с URL тоже допустим, но добавляет ещё один сервис, права загрузки и резервное копирование. Само хранение ссылки не гарантирует доступность файла. Ошибка фотографий на Cielixir не доказывает проблему PocketBase: надо отдельно проверить URL, ответ 404/403, сохранность storage, прокси /api/files, HTTPS и режим protected. Для публичного портфолио не сохраняем краткоживущие подписанные ссылки.

Резервная копия базы и локальных файлов, отдельная копия вне VPS; если файлы внешние/S3, их копируем отдельно. Никаких оригиналов/паролей в GitHub. Храним оптимизированные web-версии картинок, исходники оставляем у автора. Доступ к внешнему сервису из админки организуется серверной подписью или ограниченным upload-профилем после выбора провайдера; секретный ключ не передаётся в браузер.

Источник: https://pocketbase.io/docs/files-handling/ и https://pocketbase.io/docs/going-to-production/ .

## 8. Акцент из обложки

При загрузке обложки извлекаем несколько характерных цветов, отбрасываем почти белый/чёрный, предлагаем выразительный цвет. Сохраняем accent_auto. Автор видит образец и может указать accent_override. При смене обложки автоматический цвет пересчитывается; ручной сохраняется до сброса. Светлые цвета не используем напрямую для мелкого текста на бумаге: подбираем тёмный вариант с читаемым контрастом; бейдж выбирает светлый либо тёмный текст. Цвета должны быть валидным HEX. Автоматика — помощник, а не гарантированно правильный художественный выбор.

Код страницы использует одну локальную переменную --project-accent; глобальные цвета и шрифты не дублируются. Вычисление по файлу на загрузке позволяет не зависеть от CORS внешней картинки при каждом открытии страницы.

## 9. Права и публикация

Публичные list/view показывают только published. Категории доступны для чтения. Дочерние медиа/этапы читаются только для published-проекта либо редактором. Create/update/delete контента — только авторизованным аккаунтам из editors. Создание, изменение и удаление аккаунтов с публичного API закрыто; существующий редактор может читать собственный профиль. Права задаются API rules PocketBase, а не только скрытой кнопкой в интерфейсе.

Важно: public file в PocketBase доступен знающему URL, даже если запись — черновик. Если черновые изображения должны быть приватными, используют protected + корректное viewRule и авторизацию; для внешнего хранилища нужна аналогичная настройка. В первой версии черновики скрывают страницу, но не обещают секретность загруженных файлов.

Проверки при сохранении/публикации повторяются на стороне PocketBase (rules/hooks), а не только в форме: slug, год, одна категория, статус, FR-текст, своя обложка, число изображений, валидные URL/HEX, типы blocks, порядок этапов и принадлежность detail-медиа. Индексы: unique slug; unique (project, position) у этапов; индексы category, status и project у дочерних коллекций. Положительные ранги опубликованных работ должны быть уникальны; нулевые — нет. Смена двух позиций делается атомарной операцией либо безопасным серверным пересчётом, а не несколькими независимыми запросами браузера.

Источник API rules: https://pocketbase.io/docs/api-rules-and-filters/ .

## 10. Будущая админка и публикация сайта

Форма редактирования имеет вкладки «Основное», «Галерея», «Характеристики», «Этапы», «Публикация». В текстовых полях переключатель FR/EN/RU. Редактирование сохраняет черновик, затем предпросмотр, затем публикация после проверок. Новая работа не появляется случайно в каталоге. Заполнение проекта с медиа выполняется последовательно: черновик проекта → медиа → выбор обложки → этапы → публикация. Из-за этой последовательности cover не отмечается как always-required в схеме коллекции: обязательность проверяется при публикации.

Перед подключением надо решить, как обновляется публичный Astro-сайт. При статической сборке изменение базы не обновляет HTML автоматически: потребуется запуск новой сборки. Для ожидаемого «сохранила — работа появилась» предпочтительны серверно формируемые страницы или явный webhook пересборки. Конкретный адаптер Netlify/VPS выберем на этапе интеграции, не сейчас. Не обещаем мгновенное обновление, оставив текущую статическую сборку без изменений.

Следующие шаги: подтвердить структуру → перенести MCD в Looping для учебной работы → согласовать хостинг медиа → создать локальную PocketBase с миграциями и API rules → наполнить четырьмя примерами → написать общий шаблон и каталог → сделать редакторскую админку → выбрать способ публикации.
